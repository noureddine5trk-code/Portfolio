Report model: user enumeration and identifier disclosure on an account-existence endpoint

user-enumerationinfo-disclosureapireport-model

Sanitized model: placeholders only, illustrative values. See the safe-testing checklist before testing anything.

Placeholders

PlaceholderMeaning
<TARGET_HOST>In-scope host listed by the program
<API_PREFIX>API path prefix of the account service
<YOUR_ACCOUNT_EMAIL>An account you own and registered for testing
<UNUSED_EMAIL>An address you control that is not registered

Summary

An endpoint meant to tell whether an email address is registered answers differently depending on whether the account exists, which allows user enumeration. For existing accounts it also returns an internal user identifier and a token without authentication, which is sensitive data disclosure.

Two issues

  • A — User enumeration: the two answers are binary and unambiguous, with no generic "check your email" message.
  • B — Identifier and token disclosure: an account-existence check has no reason to return either field.

Steps to reproduce

Step 1 — an existing account (your own)

curl -s "https://<TARGET_HOST>/<API_PREFIX>/user/exists?email=<YOUR_ACCOUNT_EMAIL>" \
  -H "Accept: application/json"
{
  "userId": "<REDACTED_NUMERIC_ID>",
  "userToken": "<REDACTED_TOKEN>",
  "status": "success"
}

Step 2 — an address that is not registered

curl -s "https://<TARGET_HOST>/<API_PREFIX>/user/exists?email=<UNUSED_EMAIL>" \
  -H "Accept: application/json"
{
  "error": [{ "errorCode": "<NOT_FOUND_CODE>" }]
}

Evidence (redacted)

  • Both request / response pairs side by side, with the identifier and the token masked.
  • A note that no cookie, session or authorization header was sent.

Impact

  • Enumeration: anyone can confirm which email addresses have an account, which helps phishing and credential-stuffing lists.
  • Identifier disclosure: an internal user ID is useful for testing other endpoints that take a user identifier.
  • Token disclosure: a token returned without authentication is a significant exposure on its own. State clearly what you verified, and do not speculate about what it grants.

Remediation

  • Return the same generic response whether the address exists or not.
  • Remove the user identifier and the token from this response entirely.
  • Add CAPTCHA and rate limiting for repeated or automated requests.
  • Log and alert on bulk enumeration patterns.

Writing notes

  • Test with your own account and addresses you control only. Never check real customers' emails; one request on each side is enough.
  • Many programs rate pure enumeration as low or exclude it. The identifier and token disclosure is what raises the issue, so lead with it and check the policy exclusions.
  • If you test what the token allows, do it with your own account only and say so in the report.
