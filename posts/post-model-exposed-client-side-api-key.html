Report model: third-party API key exposed in client-side JavaScript

api-keyclient-sidesecretsreport-model

Sanitized model: placeholders only, illustrative values. See the safe-testing checklist before testing anything.

Placeholders

PlaceholderMeaning
<TARGET_HOST>In-scope host listed by the program
<CONFIG_SCRIPT_PATH>Public script that ships the client configuration
<VENDOR_API_HOST>API host of the third-party service
<REDACTED_KEY>The key — always fully masked in the write-up

Summary

A key used to authenticate calls to a third-party service (here a ratings and reviews platform) is embedded in plaintext in a public JavaScript file. Anyone can read it and call the vendor API directly, which bypasses the checks the site itself performs: login, verified purchase and rate limiting.

Technical background

Such keys are normally meant to be used server-side, so that the site's backend can enforce its rules before forwarding a request. When the key ships in client-side code, those controls are skipped by anyone who calls the vendor API directly.

Steps to reproduce

Step 1 — locate the key

Load the site with DevTools or an intercepting proxy and find the script that carries the configuration: GET /<CONFIG_SCRIPT_PATH> on <TARGET_HOST>. Look for the key field:

APP.params.<service> = {
    "apiVersion": "<VERSION>",
    "instance":   "<INSTANCE>",
    "passKey":    "<REDACTED_KEY>",
    "submitUrl":  "https://<VENDOR_API_HOST>/<SUBMIT_ENDPOINT>"
};

Step 2 — show the key is accepted without any site credentials

Send a single request to the vendor API with no cookies and no session. Use the least intrusive form: a preview / validate-only mode if the vendor offers one, otherwise one clearly labelled test entry, within what the program rules allow. Never create real or bulk content.

curl -X POST "https://<VENDOR_API_HOST>/<SUBMIT_ENDPOINT>" \
  -d "passkey=<REDACTED_KEY>" \
  -d "<required_fields>=<TEST_VALUES>" \
  -d "action=<preview_or_submit>"

Step 3 — observe the response

HTTP 200, an empty error list and a submission identifier mean the request was accepted without any authentication.

Evidence (redacted)

{
  "Errors": [],
  "SubmissionId": "<REDACTED>",
  "TypicalHoursToPost": "<HOURS>"
}
  • The request that retrieves the script (key masked).
  • The vendor response showing no errors and a submission identifier.
  • A note that no cookie, token or account was used.

Impact

  • Ratings and reviews can be created outside the site's own controls, so product ratings can be pushed up or down artificially.
  • Customers and the company can no longer trust the displayed ratings.
  • The exposure may breach the terms of the contract with the vendor.
  • No login, purchase check or rate limit applies, so abuse needs very little skill.

Remediation

  • Immediate: rotate the key and remove it from every client-side file.
  • Short term: move the vendor calls to the backend (server-to-server), enforce purchase verification there, and add per-user rate limiting.
  • Long term: audit all third-party keys present in client-side code and add secret scanning to the CI/CD pipeline.

Writing notes

  • Check the vendor documentation: some keys are designed to be public and have a limited scope. A report is stronger when you show that the key is privileged or that it bypasses a control the site really enforces.
  • Mask the key consistently everywhere — summary, steps, evidence and screenshots. A partial mask in one place and the full value in another defeats the purpose.
  • Prefer a validate-only request over creating data in production.
