Report model: unauthenticated health-check endpoint exposing live metrics

info-disclosuremisconfigurationreconreport-model

Sanitized model: placeholders only, illustrative values. See the safe-testing checklist before testing anything.

Placeholders

PlaceholderMeaning
<TARGET_HOST>In-scope host listed by the program
<HEALTHCHECK_PATH>Path of the monitoring / health-check endpoint
<VALUE>, <COUNTER>Values returned by the endpoint (masked)

Summary

https://<TARGET_HOST>/<HEALTHCHECK_PATH> is reachable from the internet without authentication. It returns live production metrics: memory, token and session store sizes, transaction counters, failure counts and response-time statistics. A field name that refers to the production token store shows that this is the live system and not a staging node.

Steps to reproduce

Step 1 — one unauthenticated request

curl -s "https://<TARGET_HOST>/<HEALTHCHECK_PATH>"

Expected: HTTP 200, a JSON body, no authentication challenge.

Step 2 — confirm the data is live, not cached

Repeat the request a few times with a short pause. Counters such as total and failed transactions change between calls. A handful of requests is enough.

Evidence (redacted)

{
  "cpu.load": "<VALUE>",
  "total.free.memory": "<VALUE>",
  "token.store.<NAME>.size": "<VALUE>",
  "session.registry.size": "<VALUE>",
  "total.transactions": "<COUNTER>",
  "total.failed.transactions": "<COUNTER>",
  "response.time.max": "<VALUE>"
}
  • Raw request and response, with UTC timestamps.
  • Two responses a few seconds apart showing the counters moving.
  • The field name that proves the environment (production vs staging).

Impact

  • Infrastructure fingerprinting — counter values that differ between consecutive calls suggest several nodes behind a load balancer, which reveals the shape of the cluster.
  • Feedback side channel — a live failure counter tells an outsider whether their authentication traffic reaches the backend.
  • Environment confirmation — names in the output remove any doubt that the node is production.
  • Capacity disclosure — configured limits (for example the session store size) are exposed.

This is information disclosure, not direct compromise. Rate it honestly and describe what the data enables, not what you did not verify.

Remediation

  • Immediate: block external access to the path with the WAF or firewall.
  • Short term: allowlist only the load balancer and monitoring system address ranges.
  • Long term: audit the other diagnostic and admin paths of the same product, and alert on external hits to this path as a reconnaissance canary.

Writing notes

  • Open with the exact URL pattern and the one-line reproduction; triagers read that first.
  • Easy-to-find exposures are often reported by several people, so clear steps and timestamps help.
  • Keep the impact tied to the data actually returned.

HackerOne · Report model

Report model: third-party API key exposed in client-side JavaScript

api-keyclient-sidesecretsreport-model

Sanitized model: placeholders only, illustrative values. See the safe-testing checklist before testing anything.

Placeholders

PlaceholderMeaning
<TARGET_HOST>In-scope host listed by the program
<CONFIG_SCRIPT_PATH>Public script that ships the client configuration
<VENDOR_API_HOST>API host of the third-party service
<REDACTED_KEY>The key — always fully masked in the write-up

Summary

A key used to authenticate calls to a third-party service (here a ratings and reviews platform) is embedded in plaintext in a public JavaScript file. Anyone can read it and call the vendor API directly, which bypasses the checks the site itself performs: login, verified purchase and rate limiting.

Technical background

Such keys are normally meant to be used server-side, so that the site's backend can enforce its rules before forwarding a request. When the key ships in client-side code, those controls are skipped by anyone who calls the vendor API directly.

Steps to reproduce

Step 1 — locate the key

Load the site with DevTools or an intercepting proxy and find the script that carries the configuration: GET /<CONFIG_SCRIPT_PATH> on <TARGET_HOST>. Look for the key field:

APP.params.<service> = {
    "apiVersion": "<VERSION>",
    "instance":   "<INSTANCE>",
    "passKey":    "<REDACTED_KEY>",
    "submitUrl":  "https://<VENDOR_API_HOST>/<SUBMIT_ENDPOINT>"
};

Step 2 — show the key is accepted without any site credentials

Send a single request to the vendor API with no cookies and no session. Use the least intrusive form: a preview / validate-only mode if the vendor offers one, otherwise one clearly labelled test entry, within what the program rules allow. Never create real or bulk content.

curl -X POST "https://<VENDOR_API_HOST>/<SUBMIT_ENDPOINT>" \
  -d "passkey=<REDACTED_KEY>" \
  -d "<required_fields>=<TEST_VALUES>" \
  -d "action=<preview_or_submit>"

Step 3 — observe the response

HTTP 200, an empty error list and a submission identifier mean the request was accepted without any authentication.

Evidence (redacted)

{
  "Errors": [],
  "SubmissionId": "<REDACTED>",
  "TypicalHoursToPost": "<HOURS>"
}
  • The request that retrieves the script (key masked).
  • The vendor response showing no errors and a submission identifier.
  • A note that no cookie, token or account was used.

Impact

  • Ratings and reviews can be created outside the site's own controls, so product ratings can be pushed up or down artificially.
  • Customers and the company can no longer trust the displayed ratings.
  • The exposure may breach the terms of the contract with the vendor.
  • No login, purchase check or rate limit applies, so abuse needs very little skill.

Remediation

  • Immediate: rotate the key and remove it from every client-side file.
  • Short term: move the vendor calls to the backend (server-to-server), enforce purchase verification there, and add per-user rate limiting.
  • Long term: audit all third-party keys present in client-side code and add secret scanning to the CI/CD pipeline.

Writing notes

  • Check the vendor documentation: some keys are designed to be public and have a limited scope. A report is stronger when you show that the key is privileged or that it bypasses a control the site really enforces.
  • Mask the key consistently everywhere — summary, steps, evidence and screenshots. A partial mask in one place and the full value in another defeats the purpose.
  • Prefer a validate-only request over creating data in production.

HackerOne · Report model

Report model: user enumeration and identifier disclosure on an account-existence endpoint

user-enumerationinfo-disclosureapireport-model

Sanitized model: placeholders only, illustrative values. See the safe-testing checklist before testing anything.

Placeholders

PlaceholderMeaning
<TARGET_HOST>In-scope host listed by the program
<API_PREFIX>API path prefix of the account service
<YOUR_ACCOUNT_EMAIL>An account you own and registered for testing
<UNUSED_EMAIL>An address you control that is not registered

Summary

An endpoint meant to tell whether an email address is registered answers differently depending on whether the account exists, which allows user enumeration. For existing accounts it also returns an internal user identifier and a token without authentication, which is sensitive data disclosure.

Two issues

  • A — User enumeration: the two answers are binary and unambiguous, with no generic "check your email" message.
  • B — Identifier and token disclosure: an account-existence check has no reason to return either field.

Steps to reproduce

Step 1 — an existing account (your own)

curl -s "https://<TARGET_HOST>/<API_PREFIX>/user/exists?email=<YOUR_ACCOUNT_EMAIL>" \
  -H "Accept: application/json"
{
  "userId": "<REDACTED_NUMERIC_ID>",
  "userToken": "<REDACTED_TOKEN>",
  "status": "success"
}

Step 2 — an address that is not registered

curl -s "https://<TARGET_HOST>/<API_PREFIX>/user/exists?email=<UNUSED_EMAIL>" \
  -H "Accept: application/json"
{
  "error": [{ "errorCode": "<NOT_FOUND_CODE>" }]
}

Evidence (redacted)

  • Both request / response pairs side by side, with the identifier and the token masked.
  • A note that no cookie, session or authorization header was sent.

Impact

  • Enumeration: anyone can confirm which email addresses have an account, which helps phishing and credential-stuffing lists.
  • Identifier disclosure: an internal user ID is useful for testing other endpoints that take a user identifier.
  • Token disclosure: a token returned without authentication is a significant exposure on its own. State clearly what you verified, and do not speculate about what it grants.

Remediation

  • Return the same generic response whether the address exists or not.
  • Remove the user identifier and the token from this response entirely.
  • Add CAPTCHA and rate limiting for repeated or automated requests.
  • Log and alert on bulk enumeration patterns.

Writing notes

  • Test with your own account and addresses you control only. Never check real customers' emails; one request on each side is enough.
  • Many programs rate pure enumeration as low or exclude it. The identifier and token disclosure is what raises the issue, so lead with it and check the policy exclusions.
  • If you test what the token allows, do it with your own account only and say so in the report.
